Fintech — 2026

Ledgerline

A real-time treasury dashboard that shows finance teams every incoming and outgoing payment the moment it settles.

Client
Bluefin Payments
Role
Lead frontend engineer
Year
2026
Stack
TypeScript, React, Go, PostgreSQL, Kafka
Links
Live site ↗Live

The problem

Finance teams reconciled payments from nightly CSV exports. By the time a failed transfer showed up, it was a day old and the customer had already called support.

Approach

We replaced the nightly export with a Kafka event stream. A Go service folds events into per-account balances, and the React client subscribes over Server-Sent Events, so the ledger updates without a refresh.

Key decisions

  • Server-Sent Events over WebSockets. The data only flows one way, SSE works through corporate proxies, and the browser reconnects for free.
  • A virtualised table. Only visible rows are rendered, so a 50,000-row ledger scrolls at 60 fps.
  • Integer minor units everywhere. Amounts are stored and sent as cents from the database to the screen. No floats anywhere.

In the code

const events = new EventSource(`/api/ledger/${accountId}/stream`);

events.addEventListener("settled", (e) => {
  const tx: Transaction = JSON.parse(e.data);
  ledger.upsert(tx.id, tx);        // O(1) keyed update
  balance.add(tx.amountMinor);     // integer cents, never floats
});

Outcome

p95 time from settlement to screen
140 ms
fewer “where is my payment” tickets
−38%
rows scrolled at 60 fps
50k

Finance now spots failed transfers within seconds instead of the next morning. The same stream later powered customer-facing payment notifications.

Tidepool

A fast terminal log viewer that tails, filters and searches gigabytes of structured logs without leaving the keyboard.

Client
Personal open-source project
Role
Author and maintainer
Year
2025
Stack
Rust, Tokio, Ratatui
Links
Source on GitHub ↗Open source
$ tidepool api.log --where level=error12:04:31 ERROR payment timeout id=8f2c12:04:33 WARN retry 2/3 id=8f2c12:04:35 INFO settled id=8f2c 212ms12:05:02 ERROR card declined id=91ab12:05:09 INFO refund queued id=91ab_

The problem

Reading JSON logs across several services meant chaining jq, less and tail by hand, and those tools struggled on multi-gigabyte files.

Approach

Tidepool memory-maps the file, indexes line offsets in the background and parses JSON only for the lines on screen. Filters compile to a small query language, so level=error and ms>200 runs as fast as a plain text search.

Key decisions

  • Memory-mapped I/O. The operating system pages the file in on demand, so opening a 4 GB log doesn’t load 4 GB into memory.
  • Lazy parsing. A line is decoded only when it’s visible or matched by a filter.
  • One static binary. No runtime dependencies. It installs with a single command on macOS and Linux.

In the code

let mmap = unsafe { Mmap::map(&file)? };
let index = LineIndex::build_in_background(&mmap);

for line in index.visible(viewport) {
    if query.matches(line) {
        render(line);                // parse on demand
    }
}

Outcome

stars on GitHub
2.1k
to open a 4 GB log
0.8 s
contributors
37

Tidepool is now packaged for Homebrew and several Linux distributions, and two of the teams I’ve worked with use it in their on-call runbooks.

E-commerce — 2025

Kiln

A headless storefront for an independent ceramics studio whose collections sell out within hours of release.

Client
Kiln Ceramics Studio
Role
Full-stack engineer
Year
2025
Stack
Astro, TypeScript, Shopify Storefront API, Cloudflare Workers
Links
Live site ↗Live

The problem

Each release brought thousands of shoppers in the first few minutes. The old theme slowed to a crawl, and it kept selling pieces that were already gone.

Approach

Product pages are static HTML built with Astro. Live stock and cart logic run at the edge on Cloudflare Workers, and an item is reserved for ten minutes as soon as it goes into a cart.

Key decisions

  • Almost no JavaScript. Product pages ship only the add-to-cart component. Everything else is HTML and CSS.
  • Reserve stock at add-to-cart. Holding items when they enter a cart, rather than at checkout, ended overselling.
  • Sized AVIF images. Every image has explicit dimensions, so the layout never jumps while it loads.

In the code

export default {
  async fetch(req: Request, env: Env) {
    const { sku } = await req.json<{ sku: string }>();
    const ok = await env.STOCK.get(sku).reserve({ ttl: 600 });  // 10 min hold
    return Response.json({ reserved: ok }, { status: ok ? 200 : 409 });
  },
};

Outcome

Lighthouse performance score
98
conversion on release days
+12%
oversold orders since launch
0

The studio now releases collections without a support inbox full of refund requests, and hosting costs went down because most pages are static.

Collaboration — 2024

Relay

A multiplayer whiteboard where distributed teams sketch system diagrams together in real time.

Client
Studio Ferro (internal tool)
Role
Frontend engineer
Year
2024
Stack
TypeScript, Yjs, WebSockets, Canvas 2D
Links
Source on GitHub ↗Archived
ClientRelayStoreAnaSam

The problem

The team drew architecture diagrams in separate tools and pasted screenshots into docs, so every diagram was out of date soon after it was drawn.

Approach

Board state lives in a Yjs CRDT document synced over WebSockets. The canvas redraws only the regions that changed, and edits made offline merge cleanly when a laptop reconnects.

Key decisions

  • CRDTs instead of operational transforms. The server only relays messages, which kept it small and easy to run.
  • Canvas 2D instead of SVG. Boards with thousands of shapes stay smooth.
  • A separate channel for cursors. Presence updates can be dropped without affecting the document.

In the code

const doc = new Y.Doc();
const shapes = doc.getMap<Shape>("shapes");
new WebsocketProvider(RELAY_URL, boardId, doc);

shapes.observe((e) => renderer.markDirty(e.keysChanged)); // redraw only what changed

Outcome

people on one board in load tests
120
frame time with 5,000 shapes
16 ms
boards created per week at peak
40+

Relay was retired in 2025 when the studio moved to a commercial tool. The source stays public as a reference for CRDT-based editors.

AI search — 2024

Fieldnote

Semantic search across an engineering team’s docs, tickets and RFCs, with every answer linked to its source.

Client
Northstar Labs
Role
Backend engineer
Year
2024
Stack
Python, FastAPI, PostgreSQL, pgvector, React
Links
Product page ↗Live
how do we rotate API keys?RFC-112OPS-481wiki

The problem

Knowledge was spread across four tools. New engineers spent their first weeks asking questions that had already been answered somewhere.

Approach

Documents are split into passages, embedded and stored in PostgreSQL with pgvector. Queries combine vector similarity with keyword ranking, and each result cites the passage it came from.

Key decisions

  • pgvector in the existing database. No new vector database to run, back up or secure.
  • Hybrid ranking. Error codes and ticket IDs need exact keyword matches that embeddings alone miss.
  • Sources on every answer. People can check a result instead of trusting it blindly.

In the code

SELECT id, title,
       0.7 * (1 - (embedding <=> $1))    -- vector similarity
     + 0.3 * ts_rank(tsv, query)          -- keyword match
       AS score
FROM passages, plainto_tsquery($2) AS query
ORDER BY score DESC
LIMIT 8;

Outcome

passages indexed
1.2M
median query time
310 ms
repeat questions in the help channel
−45%

Fieldnote became the default starting point for onboarding, and the team later added it to their incident tooling to surface past postmortems.
